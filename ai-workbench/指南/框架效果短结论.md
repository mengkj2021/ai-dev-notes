# AI 开发框架 · 效果短结论

> 公开准备（结构7）。回答：「起票制 + prompts/workbench 这套，实际解决了什么？还弱在哪？」  
> 非广告；供路人与后续自己复盘。  
> **实践从哪来、边界在哪**：[AI开发实践-定位与现状.md](AI开发实践-定位与现状.md)。

## 解决了什么

1. **改动可追溯**：先有票（类型 / 验收 / 节点），再改代码；完结有复盘，避免「对话里改完就忘」。  
2. **文档与代码同闭环**：`project-docs` 跟实现走；接票强制「文档先行 / 待定不猜」；公开前用 sync-docs 纠漂移。  
3. **人机分工清楚**：人定意图与点验；AI 执行接票与落盘；提交须显式拉壳授权，降低误推。  
4. **规模可控**：拆票门槛 + 档位 + 一票一会话，减少「一张票改半个仓库」。  
5. **双工具可同步**：`shared` → `.cursor` / `.codebuddy`，规则不绑死单一 IDE。

## 还弱在哪

1. **点验仍靠人**：阶段 ② 靠真机 / 使用中发现问题起票；系统全面测试在阶段 ③ 做到演示收口即止（画面用例作历史对照）。阶段 ④ **维护与迭代**接零散 Bug / 式样 / AI 体系更新，不维护画面验证总表。
2. **单测覆盖偏窄**：有纯逻辑才「先测后写」；大量 Compose / 导航竞态仍靠真机（如返回键类 bug）。  
3. **公开包装后半仍手工**：版本 bump、clone 冒烟、CI 可选；无发版流水线。  
4. **规则与提示易腐**：常驻 rules 必须瘦；细节靠 include，新人仍要先读指南，否则会漏步。  
5. **过程可证 ≠ 过程精简**：票与文档多，对「只想看 App」的读者偏重——根 README 已尽量把 AI 层下沉到指南。

## 一句话

这套框架把「用 AI 做完一个可演示的本地 App」变成了**可重复的台账与纪律**；它换来的是可追溯与少瞎猜，代价是流程厚度，以及测试深度仍取决于人（阶段 ③ 全面测已收口；后续靠阶段 ④ 零散修补）。
