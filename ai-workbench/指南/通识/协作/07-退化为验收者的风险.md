# 4.7 协作：退化为验收者的风险

> 来源：克制架构观 · 知乎（AI 落地交流后反思）。整理：2026-09-20。  
> 著作权归作者所有。本笔记压缩论点与案例，不照搬全文。

## 一句话核心

AI 落地最大的风险不是 AI 犯错，而是用 AI 的人慢慢失去发现错误的能力，自己还觉得一切在变好。

## 退化曲线

```
判断者 ──→ 验收者 ──→ 点通过的人
  │            │             │
  │            │             └─ 让 AI 重跑、截图反馈、不问为什么
  │            └─ 跑测试、看结果、过 case；不读业务逻辑
  └─ 用脑子把业务模型过一遍，能发现「年月日写死」这种问题
```

退化不可见，因为**效率确实越来越高**。

## 五组错位（镜子表）

每组「常答」都务实、可操作；问题在于跳过了真正的判断维度。

| 维度 | 该问的 | 常答的 | 错位的本质 |
|------|--------|--------|------------|
| 知识 | **存什么**（任务相关那一点如何完整抽出） | 怎么存（MCP / 文件夹 / HTML / RAG） | 工具选型替代了「该让 AI 知道什么、什么必须留在人脑」 |
| 边界 | **该不该**让 AI 做 | 用哪个 AI（Claude Code 稳 / Codex 快） | 「该不该」维度从思考里消失；错的工具做错的事 |
| Review | 写不出来的**体感与默契** | 写成 skill 让 AI 自检 | 能写成的本来已显性化；真正起作用的写不成 if-else |
| 隐性知识 | 产生经验时的**场景与红线体感** | 把经验结论写成 skill | 隐性知识 ≠ 「还没写出来的显性知识」 |
| 故障 | 为什么**降智、如何诊断** | 别查原因，重跑 / 截图改 | 诊断能力被「最快路径 = 重试」替代 |

## 「年月日写死」案例

- **代码**：日期硬编码，所有测试通过，功能正常
- **暴露时机**：上线后某日期一过
- **测试为何测不到**：边界不在输入值上，而在「时间维度」
- **谁发现**：只有人把业务模型过一遍才看得见
- **性质**：不是 bug，是业务理解偏差。AI 犯错好修，这种**没人看见的偏差**上线后才暴露

## 防御性代码 vs 业务逻辑

AI 补边界靠堆防御代码：空值判断、重试、异常捕获、参数校验。

- 「看起来很健康」，体积常**大于**核心业务逻辑
- 把真正的业务逻辑盖住，review 时难穿透
- 测试 case 写不全——你不知道哪些边界没覆盖

能写成 skill 的 review 规则，**本来就已经显性化**。  
写不成的（"这里为什么这么判断"、"三年前为什么被改坏"、"字段为什么非空"），才是真正起作用的。

## 隐性知识的性质

隐性知识 ≠ 「还没写出来的显性知识」。

skill 能传的是「经验的结论」，传不了：

- 当时场景多惊险
- 为什么这条规则是**红线**而非建议
- 什么边界下可以例外

这是**知识本身的性质问题**，不是技术问题。当成待文档化条目处理就搞错了。

## 工具选型遮蔽判断的三个征兆

| 征兆 | 反向自检 |
|------|----------|
| 讨论 AI 落地只聊工具（MCP / RAG / Skill） | 「这件事 AI 必须知道什么、什么必须留在人脑」过一遍了吗 |
| 用「用哪个 AI 更快更好」回答「该不该做」 | 这件事本身就不该让 AI 做？还是只是工具没选对 |
| 「再跑一次就好」成为默认反应 | 上次为什么不好查了没有，下次还会不会重蹈 |

## 抗退化的两条纪律（候选）

1. **每周留时间通读一段核心业务代码**——不为找 bug（测试能找），为避免退化成「点通过的人」
2. **交叉审查加一条**：防御代码体积显著大于业务逻辑时报警，避免管道代码淹没域逻辑
