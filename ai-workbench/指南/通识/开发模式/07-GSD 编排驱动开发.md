# 3.7 GSD 编排驱动开发（给 AI 团队配个项目经理）

GSD（Get Ship Done，官方仓库 github.com/open-gsd/gsd-core）来自一场真实项目演讲：用 AI 从零做一个「工时管理系统」，7 个版本、34 个阶段、120 张任务卡，全部走同一套流程上线。它想解决的核心问题是：

> **AI 很能干，但不可靠。怎么把一个 2 个月的大项目放心交给它？**

把它看成「3.1 SDD 的完整运行时版」：SDD 回答**做什么**，GSD 再补四个问题——**现在干到哪一步了？由谁继续？凭什么说做完了？什么时候能发布？**

## 为什么需要它：AI 的三个毛病

| 毛病 | 表现 | 后果 |
|------|------|------|
| 金鱼记忆 | 新开对话就忘了上次的约定 | 项目无法跨会话推进 |
| 迷之自信 | 说「做完了」，其实没接上线 | 交付不可信，返工 |
| 没有纪律 | 多 Agent 并行没人统筹 | 各自为战、互相覆盖 |

人写代码也有这些问题，但人可以被「项目管理制度」约束；AI 没有自觉，GSD 就把这套制度**做成了文件结构和流程**，硬性约束它。

## 三件套：剧本、台账、按单干活的工人

| 概念 | 大白话 | 解决 AI 的哪个毛病 |
|------|--------|------|
| `.planning/` 文件夹 | **工程日志/剧本**：目标、需求、决策、进度、下一步，全写在纸面上 | 金鱼记忆（谁来看日志都能接着干） |
| Git（原子 commit） | **台账**：每步改动单独记一笔，可查可退 | 没有纪律（出问题知道是哪笔） |
| 短命子代理 + 工单 | **按单干活的工人**：每次只给一张工单和必需信息，干完写完工说明 | 迷之自信（动作可核、范围被锁） |

核心口诀：

> **会话会消失，但计划与证据必须留下。**

## 四道工序（Phase Loop）：像拍戏

一次排戏要走四道工序，GSD 把每个大版本（Milestone）拆成若干「阶段」（Phase），每阶段都走这四步：

**① 对词（Discuss）**
把「说不清楚、要拍板的地方」拿出来聊出定论，写进剧本（CONTEXT.md）。比如「多条历史记录保留哪条」「按钮点下去要不要记审计」。
→ 防止 AI 到写代码时才临场乱猜。决策写成一句话，之后谁都能引用。

**② 分镜（Plan）**
把本阶段拆成一张张「工单」（PLAN），每张写清六要素。工单就是给新 Agent 的任务卡，让它**不用猜也能干**：

| 工单字段 | 大白话 | 防的坑 |
|----------|--------|--------|
| OBJECTIVE | 为什么做、交什么出来 | AI 跑偏方向 |
| FILES | 只准动哪些文件 | 乱改无关代码 |
| ACTION | 具体怎么做、复用哪个现成模式 | 凭空发明风格 |
| VERIFY | 用什么命令/观察来证明 | 「我觉得行」 |
| DONE | 什么条件算「真完了」（非黑即白） | 「基本完成」糊弄 |
| WAVE | 和谁可同时干、必须等谁 | 并行打架 |

**③ 开拍（Execute）**
把工单发给独立的「演员」（短命子代理），**一人只背当前这张工单**（Fresh Context）。每完成一张工单，单独存一次档（原子 commit，test → feat → docs 分笔），收工写「完工说明」（SUMMARY）：真做了啥、改了哪些文件、和计划有没有偏差。偏离必须写明，不许静默扩范围。

**④ 看回放（Verify）**
**别听演员说「演完了」，场务亲自核。** 从目标反推四问：
1. 什么必须为真？（Truths）
2. 该有的东西存在、且有实质内容吗？（Artifacts）
3. 是真接通了，还是摆了个空壳？（Wiring，比如按钮后是空函数、列表是写死的空数组）
4. 测试到底证明了什么？（Tests）

验收不过 → 开「补救工单」（gap plan）→ 重验，直到过关。

四道工序走完且验收通过，才能「发布」（Ship）：把整个阶段做成 PR/MR、写归档、打版本标签。**验证先于声明完成**，这是铁律。

## 三招让「并行」不翻车

1. **Wave 分波**：互不依赖的工单放同一波并行；必须等前一步的放后面。每波结束时以 commit + 完工说明为准交接。
2. **故意串行也是策略**：语义要「先改 A 才能设计 B」时，强行并行 = 在错误地基上返工。串行 ≠ 慢。
3. **Git 当线程**：工单对应分支/工作区 → 原子 commit → 完工说明当索引 → 合流 PR。每个 Agent 之间不靠嘴传递，靠 Git。

## 档位：不是什么都走全套

| 档位 | 什么时候用 | 留什么 |
|------|-----------|--------|
| Fast | 一两分钟、一句话能说清的小改 | 直接改 + 原子 commit |
| Quick | 小功能，但需要计划或测试 | 工单 + 完工说明 |
| Full Phase | 大灰区、迁移、安全、多依赖 | 四道工序全套（对词到验收） |

真实项目大部分改动走前两档，GSD 才用得动。

## 一个容易被忽视的设计：脚本控状态

`.planning/` 里的进度文件（STATE.md）不让 Agent 随便编辑，而是用脚本（gsd-tools.cjs）更新：校验字段、固定格式、状态变更本身也进 Git。
→ 道理：**状态机是总账，不能交给记性差的人乱涂**。人也能靠脚本获得流程自动化。

## 什么时候用 / 别用

| 适合 | 不适合 |
|------|--------|
| 功能边界清楚的大项目 | 纯探索、试想法 |
| 跨很多天、多会话的大活 | 需求天天变 |
| 需要多 Agent 并行 | 就改一个小 bug |
| 要向人证明「真做完了」（可审计） | 无人验收、纯全自动（GSD 不替你补决策） |

本质是：把传统软件工程的项目管理办法（拆解、验收、归档、发布门禁）显式教给 AI。**项目越大、越乱、越需要追溯，越划算。**

与 [GitHub Spec Kit](01-SDD%20规约驱动开发.md) 比：Spec Kit 给命令和模板，GSD 给状态机与证据。与 Cursor Projects 比：Projects 给协调器和云算力，GSD 给「凭什么算完」的纸面纪律。可以叠用，不要互相替代验收。

## 给个人的轻量版（不引整套也能抄）

1. **工单化**：交给 AI 的任务先写清「只准动哪些文件 + 怎么验证 + 什么叫完成」，不许它自由发挥。
2. **完工说明**：每次让它留一句「改了啥、动了哪些文件、偏离了计划哪里」——这是跨会话唯一的可靠记忆。
3. **反向验收**：别问「做完了吗」，改问「什么必须为真？证据呢？是真接通还是空壳？」

## 术语对照

| GSD 术语 | 大白话 |
|----------|--------|
| Milestone | 一个可发布的版本 |
| Phase | 阶段，一次排戏的四道工序 |
| PLAN | 工单 |
| Wave | 工单分组，同组可并行 |
| CONTEXT / RESEARCH | 讨论定稿 / 调研记录 |
| SUMMARY | 完工说明 |
| VERIFICATION / UAT | 技术验收证据 / 人肉验收记录 |
| Ship | 发布会（生成 PR、归档、打 tag） |
| Workstream | 独立小分队（各记各的账，共享仓库） |
