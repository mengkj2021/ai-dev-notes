# 3.2 TDD 测试驱动开发

TDD + AI：**人写测试**，**AI 写实现**。测试即最精确的 Spec。

## 与传统 TDD 对比

| | 传统 TDD | TDD + AI |
|---|----------|----------|
| 流程 | 人写测试 → 人写代码 | 人写测试 → AI 写代码 → 人验证 |
| 红-绿-重构 | 全程人执行 | 红（人）→ 绿（AI）→ 重构（AI+人） |
| 人力 | 大 | 写测试 + Review |

## 流程

```
人写测试（定义行为边界）
    ↓
测试文件 + 上下文交给 AI
    ↓
AI 生成代码 → 跑测试
    ↓
失败 → AI 根据报错修改 → 再跑
    ↓
通过 → 人 Review + 补充边界测试 → 合并
```

## 价值

- 测试即 Spec，无需重复写规格
- 结果客观，不靠「看起来对」
- 边界由测试强制覆盖
- 重构有安全网

## 适用 / 不适用

| 适合 | 不适合 |
|------|--------|
| 后端 API、纯逻辑 | 前端 UI 视觉 |
| 已有测试体系的存量项目 | 快速原型 |
| 支付、权限等高正确性模块 | 需求频繁变动的早期 |

需求模糊时测试难覆盖全边界，见 [1.5 避坑手册](../基础/04-AI%20开发避坑手册.md) 问题 9。
