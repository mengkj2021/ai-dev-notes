# 1.7 上下文工程

Prompt 工程管「怎么写指令」；**上下文工程**管「这一次推理窗口里放哪些 token」。Agent 多轮循环会不断产生可进窗口的信息，必须每轮筛选。依据：Anthropic《Effective context engineering for AI agents》。

## 为什么窗口变大仍要管

- Transformer 注意力是 n²，token 越多，单位注意力越稀
- **Context Rot**：窗口填满后，召回与长程推理精度下降（不只是 Lost in the Middle）
- 上下文是有限注意力预算，边际收益递减

原则：用**最小充分、高信号**的 token 集，最大化期望行为。

## 三类策略

| 策略 | 做法 | 适用 |
|------|------|------|
| 预检索（RAG 等） | 推理前把 Top-K 塞进 Prompt | 内容相对静态、要速度 |
| Just-in-time | 只留路径/链接/查询，Agent 用工具按需加载 | 代码库、动态文档 |
| 混合 | 少量常驻（如 `AGENTS.md`）+ 工具探索 | 日常编码 Agent |

Claude Code / Cursor Agent 典型混合：规则文件预先注入，文件用 glob/grep 即时读。

## 长任务三件套

窗口总会脏。长程 Agent 靠这三招，而不是指望无限窗口：

| 招 | 作用 |
|----|------|
| Compaction（压缩） | 旧轮次收成摘要，腾出注意力 |
| 结构化笔记 | 进度、决策写进文件（如 `.planning/`、Project 共享上下文），会话可死文件活 |
| Subagent | 脏活在干净窗口做，只回 1–2K token 摘要 |

与 [3.7 GSD](../开发模式/07-GSD%20编排驱动开发.md)、[Cursor Projects](../工具/03-Cursor%20使用.md) 同一思路：**会话会消失，计划与证据必须留下。**

## Skill 怎么进上下文

渐进披露三层：元数据 → `SKILL.md` 正文 → 引用文件/脚本输出。详见 [1.1](01-基础概念.md) Skill、[4.3](../协作/03-Skill%20与%20Rules%20驱动.md)。

## 反模式

| 反模式 | 后果 |
|--------|------|
| 把 Wiki/规范全塞进 System Prompt | 注意力被稀释，中间规则失效 |
| MCP 工具堆几十个且职责重叠 | 选错工具 |
| 多 Agent 默认上、上下文边界不清 | 污染 + token 暴涨 |
| 只信「窗口 1M 所以整库粘贴」 | Context Rot，费用按长上下文倍率计 |

工具返回值也要短：摘要、diff、错误片段，不要整份日志。
